# 企业微信扫码登录 Quick：新客户首次部署

> 本页是独立临时用户方案的**初始阶段**，会创建无本地密码的过渡 Keycloak 员工。完成后必须继续 [管理员映射临时用户实施](管理员映射临时用户实施.md)，启用受控会话复用，并在验收后显式清理过渡账号。仅做本页不是最终 Users=0 状态。

需要不运行本项目脚本、逐项在控制台配置？使用 [完整手动配置图文说明](完整手动配置图文说明.md)。同一 Realm 的手动和自动化路径不要混用。

**适用范围：客户只完成了 Keycloak 26.6.4 和社区 wecom 插件安装。Realm、员工、AWS 联合登录和 Quick 登录配置都还没有。** 从第 1 步开始，不需要先部署本项目管理平台，不使用测试环境的账号、Secret 或资源。

本页使用 **1.0.1 客户实施包**。脚本创建 Keycloak 配置、IAM 资源及经确认的 Quick 用户；企业微信后台、Quick 订阅和 Quick SSO / Desktop 表单保留人工操作。服务器、域名和 HTTPS 属于现有 Keycloak 安装，不由本包新建。已有业务环境请改读 [已有环境扫码接入](已有环境扫码接入.md)，不要用首次初始化去覆盖。

## 1 · 开通 Quick，准备企业微信应用

### Quick（客户管理员操作）

登录**目标客户 AWS 账号**，打开 Amazon Quick，选择准备使用的区域。如未开通，按注册向导选择支持本方案的 **Enterprise / Enterprise and Q** 订阅和 **IAM 联合身份兼容的身份方式**，核对当前费用后由客户确认开通。保留独立管理员登录方式。

脚本不创建订阅、不转换已有 IAM Identity Center / AD 账号。开通后需可进入 Quick 管理账户，并有 `default` 命名空间。没有这些条件时，检查命令会停止。注册向导未在本次客户现场实拍，选项和收费以客户当前页面为准。

![Quick 管理账户入口](screenshots/06-quick-admin-navigation.png)

### 企业微信（企业管理员操作）

进入 **企业微信管理后台 → 应用管理 → 自建 → 创建应用**。填写应用名称，把获批员工加入可见范围。已有合适应用可复用。

![自建应用的 AgentID、Secret 和可见成员](screenshots/01-wecom-application.png)

- **CorpID**：我的企业 → 企业信息 → 企业 ID。
- **AgentID**：自建应用详情页。
- **Secret**：该应用 Secret → 查看。若提示通过“企业微信团队”下发，由管理员点发送，在自己的企业微信客户端查看消息。下一步安全录入，**不要写进 JSON、工单或聊天**。
- **员工 UserId**：通讯录 → 员工详情 → 账号；不是显示姓名或邮箱。

![企业微信开发者接口](screenshots/02-wecom-features.png)

在应用下方开发者接口配置：

| 位置 | 填写内容 |
|---|---|
| 企业微信授权登录 → Web 网页 → 授权回调域 | 客户 Keycloak 域名，例如 `sso.example.com`；不带协议、路径 |
| 网页授权及 JS-SDK → 可信域名 | 按后台要求验证同一域名；不能替代上一项 |
| 企业可信 IP | Keycloak 服务器实际公网出口 IP，多个出口全部添加；不是浏览器、本机或 ALB IP |

![授权回调域的位置](screenshots/03-wecom-qr-domain.png)

若要求 `WW_verify_*.txt`，下载本企业文件，让服务器管理员原样发布到 Keycloak 域名根路径，再回企业微信验证。不要更改文件内容或关闭 HTTPS。确认浏览器访问 `https://客户Keycloak域名/WW_verify_实际文件名.txt` 能直接显示原始文件内容（不需登录、不跳转），再点击验证。

## 2 · 上传配置包，填客户参数

在目标 AWS 账号打开 **CloudShell → Actions → Upload file**，上传 `quick-wecom-transient-sso-v1.0.1.zip`。依次复制执行：

```bash
quick_wecom_dir="$(mktemp -d ./quick-wecom.XXXXXX)"
unzip -n quick-wecom-transient-sso-v1.0.1.zip -d "$quick_wecom_dir"
cd "$quick_wecom_dir/quick-wecom-transient-sso"
python3 --version
python3 -c "import boto3; print(boto3.__version__)"
python3 scripts/new_customer.py --version
cp config/new-customer.example.json customer.json
nano customer.json
```

应显示 Python 3.10+、boto3 版本、脚本版本 `1.0.1`。缺少 boto3 时，经客户允许运行 `python3 -m pip install --user boto3==1.43.110`。ZIP 若被改名，用 `ls -l *.zip` 查实际名称并替换解压命令中的文件名。**不能只上传 ZIP 就运行之前目录的旧脚本。**

填好字段，在 nano 中按 Ctrl+O、Enter 保存，Ctrl+X 退出：

| 字段 | 填什么 |
|---|---|
| `origin` | Keycloak HTTPS 地址，例如 `https://sso.example.com`，末尾不加 `/` |
| `realm` | 要新建的业务 Realm，例如 `customer-quick`；不能是 `master` 或已存在的 Realm |
| `aws_account` / `region` | 客户 12 位 AWS 账号、Quick 身份区域 |
| `corp_id` / `agent_id` | 第 1 步记录的企业 ID / 应用 AgentID |
| `secret_parameter` | 客户独立的 SSM 路径，例如 `/customer-quick/wecom-secret`；不是 Secret 值 |
| `saml_alias` | 本 Realm 登录别名，例如 `quick-web`，脚本生成完整登录地址 |
| `users[].username` | 新建员工用户名，小写，2–64 位字母、数字、点、下划线或连字符 |
| `users[].email` | 已核实的员工邮箱；作为 Quick 身份和信任条件，不自动认领已有用户 |
| `users[].wecom_user_id` | 真实企业微信账号，保留原始大小写 |
| `users[].quick_role` | 明确选择 `READER_PRO` 或 `AUTHOR_PRO`，费用由客户批准 |

初始清单支持 1–25 位员工。**不用填写 Keycloak UUID、Role ARN、SAML Provider ARN、Quick 用户名或 Metadata。** 脚本会创建并读取这些值。必须替换模板的全部示例值。

## 3 · 保存 Secret，预检查

以下命令均在刚解压的目录执行。先从你填写的 JSON 读取参数，不用重复手填账号：

```bash
quick_account="$(python3 -c 'import json; print(json.load(open("customer.json"))["aws_account"])')"
quick_region="$(python3 -c 'import json; print(json.load(open("customer.json"))["region"])')"
quick_secret_path="$(python3 -c 'import json; print(json.load(open("customer.json"))["secret_parameter"])')"
quick_target="$(python3 -c 'import json; c=json.load(open("customer.json")); print(c["aws_account"]+"/"+c["realm"])')"
python3 scripts/new_customer.py plan --config customer.json
python3 scripts/store_secret.py --account "$quick_account" --region "$quick_region" --parameter "$quick_secret_path"
python3 scripts/new_customer.py check --config customer.json
```

`store_secret.py` 提示后粘贴企微 Secret，输入不回显，保存为 SSM **SecureString**。已有参数不会覆盖；已成功保存就跳过该条，轮换另走批准流程。`plan` 只展示计划和收费清单；`check` 检查账号、Quick 订阅、插件及同名/同邮箱冲突，不创建资源。

在线命令会提示 Keycloak 管理账号和隐藏密码。启用了 MFA 的客户**不能关闭 MFA 来运行脚本**：运维用批准的短期 `QUICK_SSO_ADMIN_TOKEN`，或增加 `--admin-secret-id` 引用客户自己 AWS Secrets Manager 中 `{username,password}` 管理凭据。不要把密码/Token 放在命令参数中。

权限清单见 [首次部署权限与恢复](首次部署权限与恢复.md)。重新打开 CloudShell 后，先回到原解压目录，再执行本节四条变量赋值；不要换目录重新初始化。

## 4 · 自动创建 Keycloak 和 AWS 配置

```bash
python3 scripts/new_customer.py keycloak --config customer.json --directory customer-run --confirm-target "$quick_target"
python3 scripts/new_customer.py aws --config customer.json --directory customer-run --confirm-target "$quick_target"
```

**第一条：** 新建 Realm、Web SAML 和 Desktop Public/PKCE 客户端，创建员工和精确企微绑定，配置拒绝未绑定员工的流程。员工没有本地密码，扫码 Provider 暂不启用。不改 `master`，不依赖管理平台数据库。

**第二条：** 生成并提交 CloudFormation 堆栈，创建一个 SAML Provider 和**每位员工一个 IAM 联合角色**。角色仅信任当前 Realm、该员工用户名和邮箱，不授 AWS 管理权限，并禁止登录时自动注册 Quick 席位。单人单角色避免多人信任文档超长；名称和 ARN 均自动生成。

首次可能显示 `SUBMITTED` 或 `CREATE_IN_PROGRESS`。这是进行中，**不能直接进入下一步**。到 AWS → CloudFormation 查看本次 `QuickSSO-...` 堆栈，待完成后重复第二条命令，直到显示 `aws_ready: true` / `CREATE_COMPLETE`。脚本不会再次创建或替换堆栈。

本地 `customer-run` 生成：

| 文件 | 用途 |
|---|---|
| `parameters.json` | Quick 手工填写的实际地址和客户端参数 |
| `metadata.xml` | 当前 Realm Metadata；已自动交给 AWS，无需手工重复上传 |
| `employees.json` | 真实 UUID、员工与 Quick 身份对应关系、ARN |
| `aws-template.json` | 本次 AWS CloudFormation 配置 |
| `state.json` | 恢复检查点，必须保留，不能编辑或丢弃 |

下载 Metadata：CloudShell → Actions → Download file，填写**原工作目录下 `customer-run/metadata.xml` 的路径**；用 `pwd` 查看当前目录。文件不含密码，但客户标识和员工清单仍按内部资料保管。

## 5 · 确认费用，自动创建 Quick 用户

重新展示计划，核对每位员工的邮箱、Quick 角色和人数。得到客户的收费许可批准后执行；**不需要再去 Quick 邀请一遍用户**：

```bash
python3 scripts/new_customer.py plan --config customer.json
read -r -p '核对收费清单并获批准后，粘贴 plan 中 confirm_paid_users 的完整值：' quick_paid
python3 scripts/new_customer.py users --config customer.json --directory customer-run --confirm-target "$quick_target" --confirm-paid-users "$quick_paid"
```

应显示 `paid_users_verified` 与清单人数一致。确认值绑定人数和角色清单，不能填 `yes`。同邮箱/同名已有用户会停止，不重复收费、不自动关联。创建结果不明确时保留原目录核查，不能重新解压来重试注册。

Keycloak UUID 与 Quick 身份已自动对应，无需“手动导入关联”。本版是**固定清单的首次部署器**：重复运行同配置可验证/续跑，不支持直接修改这份 JSON 来追加或改名员工。

## 6 · Quick 中手工配置三个位置

查看实际参数：

```bash
cat customer-run/parameters.json
```

### ① Web SSO

进入 **Quick → 管理账户 → 身份 → SSO**，新增配置。IdP URL 填 `parameters.json` 中 **`quick_sso_url`**，重定向 URL 参数填 **`RelayState`**。保存配置，保留页面给出的独立管理员应急入口；先用测试入口验证，再按客户批准开启重定向。

![Quick Web SSO 实际设置页](screenshots/10-quick-sso-settings.png)

图中旧值已遮盖，文字“平台当前 Realm”在本独立部署路线对应 `customer-run/parameters.json`。**不要照抄截图域名，不要把 `metadata_url` 填到 IdP URL。** 扫码到第 7 步才启用；现在填表，之后完成扫码验证。

### ② Desktop 扩展访问

进入 **管理账户 → 权限 → 扩展访问 → 添加扩展访问**，选择 **Amazon Quick / Desktop application for Quick**。

![扩展访问入口](screenshots/07-quick-extension-access-entry.png)

| 表单字段 | 从 `parameters.json` 复制 |
|---|---|
| Name | 自定，例如 `CustomerQuick-Desktop-access` |
| Issuer URL | `issuer` |
| Authorization Endpoint | `authorization_endpoint` |
| Token Endpoint | `token_endpoint` |
| JWKS URI | `jwks_uri` |
| Client ID | `client_id`，值为 `amazon-quick-desktop` |

核对后点 **Add**。这是 Public 客户端，**没有 Client Secret**，不要把企业微信 Secret 填进 Quick。Scope/PKCE 已由脚本配置；当前表单没有这些字段时无需额外填写。

### ③ Desktop 扩展

回到 **Quick 主工作区 → 扩展 → 创建扩展**，选择上一步的 Desktop access → Next → Create，确认 **Active / 活跃**。

![Desktop 扩展列表](screenshots/08-quick-extensions.png)

**扩展访问和扩展都必须创建，不需要每位员工各建一份。** 在扩展卡片中下载 Mac/Windows 客户端。图片为已有脱敏实拍，仅定位菜单和字段，不代表客户已配置成功；Desktop 创建表单仍需现场核对留证。

## 7 · 启用、扫码验收

确认企微成员、域名/IP 和 Quick 三项配置完成后执行：

```bash
python3 scripts/new_customer.py enable --config customer.json --directory customer-run --confirm-target "$quick_target" --wecom-console-confirmed --quick-console-confirmed
python3 scripts/new_customer.py verify --config customer.json
```

`enable` 核对实际 UUID、绑定、IAM 信任、RoleId、Quick 用户和收费角色后启用扫码按钮。`verify` 只验证 Web、Desktop 能跳到正确二维码入口，**不代表已进入 Quick**。

按下面顺序完成，不要跳过第 2 项：

1. **先测试直连：** 员工本人打开 `quick_sso_url` → 企业微信扫码 → 核对 Quick 账号、本人用户名/邮箱及资源。
2. **再开启账户 SSO：** 管理员回到第 6 步的 **Quick → 管理账户 → 身份 → SSO → 编辑**，将 **「服务提供商启动的 SSO」状态设为「开启」**，核对 IdP URL 和 `RelayState` 后保存。保留 `quick_emergency_url` 管理员入口。此设置影响整个 Quick 账户，应在获批窗口操作；只保存 URL、状态仍为关闭时，首次直连可能成功，但正常入口重登仍会进入原生用户名页面。
3. **验证正常入口：** 从客户区域的 Quick 登录入口重新进入。若显示账号/用户选择页，选客户自己的 Quick 账号和对应员工；选择页不是扫码页，之后才进入 Keycloak / 企业微信认证。不要选管理员或另一个同邮箱身份，不要新建账号。
4. **验证 Desktop：** 在另一台未登录的电脑或干净的客户端环境中点 **Continue with SSO**，选择实际区域，完成本人扫码，确认进入本人 Quick Desktop。再测试退出重登及持续使用；操作系统和客户端版本记入验收表。

**没有再次出现二维码不一定是错误：** Keycloak、浏览器或 Desktop 离线会话仍有效时可以复用身份。仅在 Quick 点击退出不一定注销这些会话。需要强制重新验收时，优先用另一台电脑；确需撤销会话，由管理员经批准只处理该测试员工的在线会话和 Desktop 离线会话，不要注销整个 Realm 或其他用户。只有一位获批员工时不宣称双用户隔离通过。新员工没有本地密码，不使用临时密码登录。

**暂停扫码：**

```bash
python3 scripts/new_customer.py disable --config customer.json --directory customer-run --confirm-target "$quick_target"
```

只禁用该 Realm 企微入口；不删除用户、IAM、审计或现有会话，**不会停止 Quick 席位计费**。新员工没有本地密码，禁用期间不能改用用户名密码登录；管理员走独立入口。

## 8 · 切换到最终临时用户方案

保留 `customer.json` 和 `customer-run`，继续 [管理员映射临时用户实施](管理员映射临时用户实施.md) 的第 1–6 节。清理必须在迁移扫码验收后单独批准。Quick 表单、原用户名/邮箱/角色/sub 沿用，不重新注册 Quick 用户。完成清理后后续 verify 使用新 `after-snapshot.json`，Users 应为零。
