# 企微无邮箱：管理员映射 + Keycloak 临时用户

> **仅旧持久账号环境参考。** 新客户不执行本页，不创建员工、不做 Link account、不做迁移或清理；请使用 [新客户首次部署](扫码登录快速实施.md)。本页保留旧账号核对/迁移的必要步骤，不代表新模式需要维护 Keycloak 员工。

适用于已经有 Quick 用户、AWS SAML 角色和 Keycloak 配置，希望不再维护 Keycloak 员工账号的环境。本页迁移脚本针对本项目创建的“每个员工独立 IAM 角色”配置；其他现有结构需要单独核对，不会自动改权限。

## 先看结论

企微扫码返回经过验证的 `UserId`，由管理员审批的映射表补齐原 Quick 身份；Keycloak 只为本次会话创建临时用户，不新增或修改持久员工记录。

```text
企业微信扫码（UserId）
  → 社区 wecom 插件验证身份
  → 管理员批准的映射：UserId → 原用户名、邮箱、角色、sub
  → Keycloak 临时会话
  → SAML / OIDC → 原 Quick 用户
```

这不是“完全没有身份信息”，也不是“社区插件自己补出了邮箱”：

- 需要本项目自建的 `quick-wecom-mapped-transient-v1` mapper JAR。社区 wecom 插件不改代码。
- 扩展 1.1.0 同时提供受控会话认证器，减少 Quick Desktop 在 OIDC、SAML 两段登录中重复扫码；只复用仍符合当前批准映射的临时会话。
- 不依赖企微返回 `email` / `biz_mail`。邮箱是管理员确认的 Quick 身份值，不代表企微完成了邮箱验证。
- 仍需维护批准的映射和 Quick 用户/授权；不需要创建 Keycloak 密码、手工绑定或日常维护员工账号。
- 默认保留旧 Keycloak 用户供回滚，所以刚迁移后 Users 列表不是零。完成真实扫码验收后，可按第 6 节显式清理旧账号；之后 Users 为零，批准映射及会话数据仍需保留。
- Keycloak 26.6.4 的 `transient-users` 是实验功能，mapper 使用内部 SPI。升级前必须重跑集成测试。

## 为什么不能只修改企微邮箱

本次真实调用已确认：通讯录填入邮箱后，应用的 `user/get` 仍未返回 `email` 或 `biz_mail`。普通扫码链路也未获得 `user_ticket`。因此不能把“管理后台看见邮箱”当成“应用 API 能读取邮箱”。

本方案不模拟敏感信息授权、不伪造上游邮箱，也不要求员工自己输入决定身份的字段。

## 哪些值必须保持不变

| 参数 | 来源 / 要求 |
|---|---|
| 企微 UserId | 原用户已验证的 wecom 联合绑定；插件规范化为小写 |
| Quick 用户名 / RoleSessionName | 原 Keycloak 用户名，不能改成另一个新用户名 |
| 邮箱 | 原 Quick 用户邮箱，与 IAM Email 条件一致 |
| Role ARN + SAML Provider ARN | 原 SAML Role 映射和现有 IAM 信任，不新建角色 |
| OIDC sub | 原 Keycloak 用户 UUID；迁移必须保留，不能随机生成 |
| Realm ID / CorpID / AgentID | 绑定当前 Realm 和企微应用，防止配置跨客户复用 |

批准的映射含个人信息，只保存在管理员受控配置及私有备份中，不提交 GitHub。脚本拒绝重复映射、其他账户的 ARN、不匹配的原用户，以及超出范围的 Realm。

## 1 · 安装扩展镜像

保留 Keycloak 26.6.4、原社区 wecom 插件、数据库及现有启动参数。客户包已附带 `provider/quick-wecom-mapped-transient-1.1.0.jar`，**不需要自己写代码或运行 Maven 构建**。

先在项目根目录验证扩展完整性：

```bash
(cd provider && sha256sum -c SHA256SUMS)
```

macOS 没有 `sha256sum` 时，将它替换为 `shasum -a 256`。校验不通过时停止，不部署该文件。

**容器 / ECS 部署：** 将 `YOUR_EXISTING_COMMUNITY_IMAGE_DIGEST` 替换为客户已有的 Keycloak + 社区插件镜像完整引用（例如 `registry/repository@sha256:...`），然后构建安装镜像：

```bash
docker build \
  --build-arg COMMUNITY_IMAGE=YOUR_EXISTING_COMMUNITY_IMAGE_DIGEST \
  -t quick-wecom-mapped:1.1.0 provider
```

Dockerfile 会复制附带 JAR 并启用 `transient-users`。沿用现有镜像仓库与服务器/ECS发布流程，滚动更新镜像，**不要覆盖数据库、密钥、hostname、proxy、环境变量或 Secret 引用**。所有节点健康后再执行下一步。此时 mapper 尚未启用，原登录入口仍在使用。

**非容器部署：** 由 Keycloak 运维在批准窗口将上述 JAR 安装到实际 Keycloak 目录的 `providers/`，以原服务账号执行 `bin/kc.sh build --features=transient-users`，保留原有其他 features / 数据库 / 服务构建参数，并按原启动方式重启全部节点。不要使用测试用 `start-dev` 替代生产服务。已有旧版同名扩展时先备份并替换，不能同时加载两版。

## 2 · 备份并准备

以下命令在项目根目录执行；要求 Python 3.10+、已安装项目 Python 依赖、正确客户 AWS 凭证，以及 Keycloak 管理凭证。`customer.json` 使用原部署清单，不含密码。`YOUR_ADMIN_SECRET_ARN` 是该客户已有的 Keycloak 管理员 Secrets Manager ARN，不是企微 Secret。

```bash
mkdir -m 700 mapped-private

python3 scripts/migrate_mapped_transient.py snapshot \
  --config customer.json \
  --snapshot mapped-private/before.json \
  --admin-secret-id YOUR_ADMIN_SECRET_ARN

python3 scripts/migrate_mapped_transient.py check \
  --config customer.json \
  --snapshot mapped-private/before.json \
  --admin-secret-id YOUR_ADMIN_SECRET_ARN

python3 scripts/migrate_mapped_transient.py prepare \
  --config customer.json \
  --snapshot mapped-private/before.json \
  --admin-secret-id YOUR_ADMIN_SECRET_ARN \
  --confirm-target YOUR_AWS_ACCOUNT_ID/YOUR_REALM
```

`snapshot` / `check` 只读远端。私有快照可能含企微密钥，目录权限必须 700、文件 600，不要上传或发给客户群。

使用 `--admin-secret-id` 时，脚本会在短期管理令牌到期前重新认证，不修改服务器的令牌有效期。收到明确 401 最多重试一次；网络超时、断线或服务器错误不会自动重放写操作。若自行提供静态 `QUICK_SSO_ADMIN_TOKEN`，它不会被悄悄替换。

`prepare` 会：

1. 检查快照没有过期、扩展已加载，核对原 Quick 用户与 IAM 信任。
2. 新建但暂不启用 `wecom-mapped` IdP；使用原应用的 SSM SecureString，不另建企微应用。
3. 新建受限认证流程和批准映射，调整用户属性权限，禁止员工修改身份字段。
4. 为原 Desktop 客户端增加稳定 `sub` 映射；没有该属性的旧用户仍使用原 UUID。

为什么用新别名：Keycloak 会先查已有联合绑定，复用 `wecom` 可能直接命中原持久用户，跳过临时用户创建流程。新别名避免这个问题，不必删除旧用户。

`prepare` 是一次性准备，不会自动覆盖同名配置。失败后先核对部分创建结果或回滚，不要反复盲跑。若准备过程已创建少量新对象，它们保留用于检查；回滚不会删除整个 Realm。

## 3 · 启用

```bash
python3 scripts/migrate_mapped_transient.py enable \
  --config customer.json \
  --snapshot mapped-private/before.json \
  --admin-secret-id YOUR_ADMIN_SECRET_ARN \
  --confirm-target YOUR_AWS_ACCOUNT_ID/YOUR_REALM

python3 scripts/migrate_mapped_transient.py verify --active \
  --config customer.json \
  --snapshot mapped-private/before.json \
  --admin-secret-id YOUR_ADMIN_SECRET_ARN
```

启用新 IdP，将 Realm 浏览器流程指向它，禁用旧 `wecom` 入口，禁用本地密码/重置流程。配置回读失败则尝试恢复原设置；若恢复也失败，脚本会报错，需按私有快照人工恢复。

**不会做的事：** 不新增或删除 Quick 用户，不改 IAM 角色/信任，不创建 SAML Provider，不删除旧 Keycloak 用户/绑定，不批量注销现有会话。

Quick 的 Web SSO URL、OIDC issuer、客户端 ID 和 AWS SAML 配置不变。企微回调路径变为 `/realms/YOUR_REALM/broker/wecom-mapped/endpoint`，域名仍相同；核对应用的可信域名/登录授权设置允许该地址。

## 4 · 启用 Desktop 同一次会话免重复扫码

如果前面已完成管理员映射迁移，只需先把扩展镜像升级为 **1.1.0**，再运行本节；不要重新生成快照或重复运行映射 `prepare`。

```bash
python3 scripts/migrate_mapped_sso.py prepare \
  --config customer.json \
  --snapshot mapped-private/before.json \
  --admin-secret-id YOUR_ADMIN_SECRET_ARN \
  --confirm-target YOUR_AWS_ACCOUNT_ID/YOUR_REALM

python3 scripts/migrate_mapped_sso.py enable \
  --config customer.json \
  --snapshot mapped-private/before.json \
  --admin-secret-id YOUR_ADMIN_SECRET_ARN \
  --confirm-target YOUR_AWS_ACCOUNT_ID/YOUR_REALM

python3 scripts/migrate_mapped_sso.py verify \
  --config customer.json \
  --snapshot mapped-private/before.json \
  --admin-secret-id YOUR_ADMIN_SECRET_ARN
```

这一步只新建并绑定 `quick-mapped-sso-browser` 流程，不改 Quick、IAM 或员工账号。它先校验临时会话的有效性、当前批准映射及全部身份字段；不通过才进入企微扫码或拒绝登录。**不能用普通 Cookie 执行器替代**，普通 Cookie 不会重新核对本方案的批准映射。

同一浏览器有效会话内，Desktop 的 OIDC 与 Web SAML 可共用一次扫码；不同浏览器/配置文件、Cookie 过期、服务器会话注销、`prompt=login`、`max_age` 或 SAML `ForceAuthn` 仍需重新验证。只退出 Quick 不一定同时退出 Keycloak；不要把旧会话免扫码误认为新登录已验收。

## 5 · 真实扫码验收

1. 在 Quick Desktop 退出当前账号。在它实际使用的系统浏览器中注销 Keycloak 会话或清除该 Keycloak 域名的站点 Cookie（不必清除其他网站），也可以换用无旧会话的测试电脑。再从 Desktop 启动企业登录。
2. 应出现企微二维码，用批准映射对应的员工扫码。
3. 后续 OIDC / SAML 跳转不应在同一有效浏览器会话里重复要求扫码；应进入**原 Quick 用户**，不是新用户或 AWS 角色选择页。
4. 注销 Keycloak 会话或使用无旧 Cookie 的浏览器，再从 Desktop 登录，应重新要求扫码。分别检查 Web SSO 和 Desktop。
5. 管理员核对登录事件使用 `wecom-mapped`。未清理旧账号时，Users 数量及原用户/绑定应保持不变；完成第 6 节后，应保持为零。

已有缓存登录不算新链路验收；准备成功也不等于真实企微、STS、Quick 登录已通过。

客户无需运行开发测试。请按上述五项记录真实扫码结果；脚本 verify 通过只说明配置核对通过，不等于真实企微、STS 和 Quick 登录已验收。

## 6 · 可选：清理旧 Keycloak 员工，让 Users 列表为空

仅在第 5 节真实 Web / Desktop 验收通过、且客户明确批准删除旧账号后执行。只删除快照中逐一确认的旧 Keycloak UUID，不删除 Quick 用户、IAM 角色、SAML Provider 或批准映射，也不创建新身份。

下面以待删除用户名 `employee-one` 为例，**必须替换为该客户快照中的真实旧用户名**。多个旧员工需逐个重复 `--confirm-user`；确认名单必须恰好等于快照内的旧账号名单，不支持模糊搜索或全 Realm 批量清空。

```bash
python3 scripts/retire_mapped_users.py check \
  --config customer.json \
  --snapshot mapped-private/before.json \
  --admin-secret-id YOUR_ADMIN_SECRET_ARN

python3 scripts/retire_mapped_users.py apply \
  --config customer.json \
  --snapshot mapped-private/before.json \
  --directory mapped-private/retirement \
  --admin-secret-id YOUR_ADMIN_SECRET_ARN \
  --confirm-target YOUR_AWS_ACCOUNT_ID/YOUR_REALM \
  --confirm-user employee-one

python3 scripts/retire_mapped_users.py verify \
  --config customer.json \
  --snapshot mapped-private/retirement/after-snapshot.json \
  --admin-secret-id YOUR_ADMIN_SECRET_ARN
```

`retirement` 必须是尚不存在的新目录。脚本先校验完整登录配置和 AWS / Quick 身份，再保存权限为 600 的私有备份及新核对基线，最后按准确 UUID 删除。结果应为 `persistent_employee_count: 0`、`legacy_users_removed: true`。

**清理后，所有 verify 和会话复用回滚命令都改用 `mapped-private/retirement/after-snapshot.json`。** 原 `before.json` 只作历史备份，不能继续作为“旧账号仍存在”的核对基线。若删除过程超时或中断，不要换目录盲目重试；先用新基线运行 verify，核对实际结果。部分删除失败时须人工检查，不会自动重建用户。

旧用户名、邮箱、Role pair、OIDC sub 继续作为批准映射中的值，不依赖对应持久用户行存在。再次扫码后应进入原 Quick 身份，Users 仍为零。旧账号删除可能结束其原持久用户会话；管理员应安排验证窗口。

**备份不包含可还原的密码或会话，也不保证能通过普通新增用户接口恢复原 UUID。** 清理后禁止一键退回旧“预绑定账号”登录模式；如需完整旧环境恢复，应使用客户自己验证过的 Realm / 数据库备份恢复流程。

## 回滚

若只是撤销“免重复扫码”，先执行下面命令恢复原 `quick-mapped-browser`，仍然使用管理员映射临时用户，不切回旧持久账号。新流程保留但不绑定。

```bash
python3 scripts/migrate_mapped_sso.py rollback \
  --config customer.json \
  --snapshot mapped-private/before.json \
  --admin-secret-id YOUR_ADMIN_SECRET_ARN \
  --confirm-target YOUR_AWS_ACCOUNT_ID/YOUR_REALM
```

如需退回扩展 1.0.0 镜像，先完成以上流程回滚，再恢复原镜像；不能让活动流程引用旧镜像不存在的认证器。

若要撤销整个管理员映射迁移，**仅限未执行第 6 节、旧账号仍完整存在**时执行；清理过的环境会在任何写操作前拒绝这一回滚：

```bash
python3 scripts/migrate_mapped_transient.py rollback \
  --config customer.json \
  --snapshot mapped-private/before.json \
  --admin-secret-id YOUR_ADMIN_SECRET_ARN \
  --confirm-target YOUR_AWS_ACCOUNT_ID/YOUR_REALM
```

恢复旧 IdP、Realm 登录流程和用户属性配置；禁用新 IdP，只删除本次精确匹配的 OIDC subject mapper。新流程保留供排查，旧用户和 Quick 数据不删。若扩展镜像本身故障，先用部署前保存的 ECS task definition/镜像恢复服务，再恢复 Realm。

## 后续维护边界

新增员工仍需先有经批准的 Quick 用户和正确 IAM 权限，再更新批准映射及与之对应的条件校验。不要只在后台改一段 policy：策略指纹与流程不一致会拒绝登录。当前脚本只实现已有环境一次性迁移，不提供自动增删员工接口。

禁用映射或企微成员只能限制后续身份认证，不保证立即撤销已经签发的令牌、离线会话、STS 或 Quick 会话。离职处理还需按各系统撤销会话/授权。临时用户不落员工表，但会话、日志、映射配置仍可能保存个人信息；不能宣传为“完全无用户数据”。
